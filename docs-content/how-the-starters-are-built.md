# How the starters are built

A starter is meant to be cloned and built on: what it does, an integration built from it will do
with real patients. Every rule below follows from that.

## One folder, one npm project

Each top-level folder with a `package.json` is one starter: a committed `package-lock.json`, `src/`,
`test/` and a README. There is no root project and no build step. A starter can leave the repository
on its own and still run, which is what
[Start a project from a starter](./start-a-project-from-a-starter.md) relies on.

## Synthetic data, generated at run time

Every message, document and image is generated by `@cosyte/synth` or written by hand, and must not
pass for a real record: names come from fictional pools, phone numbers from the 555 range, NPIs fail
their check digit on purpose, and ZIP codes are `00000`. Most starters generate their input from a
fixed seed on every run, so the output is the same everywhere and no fixture file is committed.
`dicom-metadata` builds its file in memory, because `@cosyte/synth` has no DICOM generator.

## Offline

No starter needs a database, an account or the network beyond localhost. The MLLP starter's
listener and client talk over `127.0.0.1`.

## Safe to copy

A pattern in a starter is one we would accept in production, or the starter's page says what to
change:

- **Bind narrowly.** The MLLP listener binds `127.0.0.1` only.
- **Acknowledge after the work.** The MLLP listener answers `AA` only after its handler finishes, so
  a durable write in the handler comes before the acknowledgement.
- **Keep values out of diagnostics.** The de-identification manifests, the transform's diagnostics
  and the CLI's notes name a position, a category and a code, never a value.
- **Fail loudly.** A check exits nonzero when it fails rather than printing a result: `deid-hl7` and
  `dicom-metadata` exit 1 when an identifier survives, `x12-remittance` when the remittance does not
  balance, and `cosyte redact` refuses to write a copy when its policy blocks a position.
- **Never fill in.** A value the input does not carry reads as missing, not as a default: the C-CDA
  starter prints `not recorded` for an absent severity, and the ASTM starter reads an unknown flag as
  `undefined`, never `normal`.

Where a starter prints a patient's name or identifier, it does so because the data is synthetic. A
production service should not write PHI to its logs.

## Self-checking

`npm test` runs the starter and asserts its key output, then checks the libraries' results against
the synthetic input, often by reading the raw input a second way, without the library. The
integration tests chain several libraries through their public APIs only. A starter's README, and
its page here, say only what the starter runs and its test asserts.

## What a starter is not

A starter is not a framework or a library: it has no API to depend on, and nothing in it is
published to npm. Copy it and own it.
